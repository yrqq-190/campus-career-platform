## M4 · 投递状态登记

### Q1 交付物清单

| # | 交付项 | 依据 |
|---|---|---|
| 1 | `ApplicationController` —— 2 个端点：`POST /api/v1/m4/applications`、`GET /api/v1/m4/applications` | 4.4 端点总览 |
| 2 | `ApplicationService` —— 状态机流转校验 + 幂等判断，明写「都在服务层」 | 4.4 分层归属 |
| 3 | `application` 表 + 唯一约束 `(student_id, job_id)` | 4.4.1 失败表 `ALREADY_APPLIED` 行；ADR-001 决策 |
| 4 | 异常映射 —— 唯一约束冲突 → `409 ALREADY_APPLIED`，非法流转 → `409 INVALID_STATUS_TRANSITION` | 4.4 开头「业务错误码仅 2 个，不可合并共用」 |
| 5 | 查询列表的空态处理 —— 无记录返回 `[]`，不报错 | 4.4.2（AC-5） |
| 6 | 单测 + 集成测（含并发重复提交用例） | 4.4.1 AC-2；S1 探针口径 |

> **注意**：M4 的边界声明写死了「不负责判断该不该投、不生成面试日程、不发送提醒」。拆任务时不得把 M6 / M3 的活塞进 M4。

### Q2 第一条任务

**建 `application` 表并落唯一约束 `(student_id, job_id)`，同时把冲突异常映射为 `409 ALREADY_APPLIED`。**

- 验收标准：**AC-2（边界）** —— 「同一学生同一岗位重复登记 → 拦截并提示已登记，返回 409 `ALREADY_APPLIED`」；对并发场景取边界表「并发重复提交」行 —— 「同一岗位两个请求同时登记，只允许一个成功，另一个返回 409」。
- 为什么排第一：S1 探针实测过这条路径（10 线程 × 100 轮，每轮写入恒为 1、500 响应为 0），ADR-001 的决策也押在这条上。表不先建，后面所有状态流转都没有落点。
- 第二条才是 `POST` 端点的正常路径（**AC-1**：已查看 → 已约面；**AC-5**：已投递 → 已约面）。
- 第三条补非法流转拦截（**AC-3**：已结束 → 已投递 被拒，409 `INVALID_STATUS_TRANSITION`）。
- **AC-4**（点外链不得自动记投递）不是 M4 的接口任务，是前端与 M3 的联动约束，拆任务时应挂到联调项，不要塞给 M4 的 Service。

### Q3 依赖

- 依赖：**M3**（读取岗位信息）。`dependency.md` §2.1：M4 直接依赖 M3，调用性质「读取岗位信息」。
- 被依赖：**M5**（读投递记录）、**M6**（范围表依赖 M4）、**M8**（经 `v_dashboard` 聚合）。
- 排期含义：M3 的岗位外链元数据先有，M4 才能落 `job_id`；M4 的 `application` 表先有，M5 的模拟面试与 M6 的面试登记才有上游依据。

## M6 · 面试登记与多级提醒

### Q1 交付物清单

| # | 交付项 | 依据 |
|---|---|---|
| 1 | `InterviewController` —— 4 个端点：`POST /api/v1/interviews`、`PATCH /api/v1/interviews/{interviewId}`、`GET .../reminders`、`GET .../calendar` | 4.6 端点总览 |
| 2 | `interview` 表 + `reminder` 表，后者唯一约束 `(interview_id, node_type)` | 4.6.1「5 条提醒写入 reminder 表，唯一约束防重复触发」 |
| 3 | 5 节点计算器 —— `D3 / D1 / H2_DEPARTURE / M30 / POST_REVIEW` | 4.6.1 成功响应 `reminders` 数组 |
| 4 | 基准兜底 —— `departureTime` 为空时前 2 小时按 `startTime` 倒推，响应标 `baselineFallback = true` | AC-8 / 边界表「基准缺失」 |
| 5 | `@Scheduled` 扫描器 —— 扫到期节点并触发推送，登记时不立即推送 | 4.6.1「由 @Scheduled 扫描生成，登记时不立即推送（FR-2）」 |
| 6 | 改期 / 取消重算 —— 清旧任务、按新时间重建，**已过期节点不触发** | AC-9 / 边界表「改期或取消后旧提醒失效与重建」 |
| 7 | 重试机制 —— 最多 3 次、间隔 5 分钟，仍失败记日志并返回 `REMINDER_SEND_FAILED` | **AC-6 / 边界表「发送失败重试」** |
| 8 | `.ics` 日历导出 | AC-4 |
| 9 | 幂等控制 —— 记录已发送状态，防扫描周期重叠重复推送 | AC-7 / 边界表「重复触发」 |

> **两处必须点出来**：
> ① 第 7 项的重试参数**在 spec 边界表里写得清清楚楚**（「最多重试 3 次（间隔 5 分钟）」），但 **4.6 契约正文里一个数字都没有**（R-06 未改）。拆任务时以 spec 为准，同时契约应补。
> ② 第 9 项的行为契约写了（「执行幂等拦截，不产生重复推送」），但 4.6 的 4 行 409 全写 `-`，`REMINDER_DUPLICATE_TRIGGER` 已撤（N-13）。前端无法按码区分四种失败，只剩 HTTP 状态码 + 提示语。

### Q2 第一条任务

**建 `interview` + `reminder` 两张表，落 `(interview_id, node_type)` 唯一约束，并把 5 个 `nodeType` 枚举落成代码常量。**

- 验收标准：**AC-1**（成功登记面试，对应 FR-1 / FR-5）+ **AC-2**（触发多级提醒，对应 FR-2）+ **AC-8**（基准缺失时前 2 小时按 `startTime` 倒推并提示）。
- 为什么排第一：5 节点和唯一约束是整章的核心实体，改期重算、幂等拦截、重试全都建在它上面。表结构错了后面全返工。
- 第二条：登记接口 + `baselineFallback` 兜底（AC-8、AC-1 的「时间冲突」「未填面试地点」两个边界行）。
- 第三条：`@Scheduled` 扫描器 + 幂等控制（AC-2、AC-7）。
- 第四条：改期 / 取消重算（AC-5、AC-9）。
- 第五条：重试与 `REMINDER_SEND_FAILED`（AC-6）。
- 第六条：`.ics` 导出（AC-4）。
- **AC-3（复盘提醒）**别漏：容易只做 5 个节点里的前 4 个，`POST_REVIEW` 就是复盘节点。
- **术语坑**：契约用 `nodeType` 枚举，spec 用「前 3 天 / 前 1 天 / 前 2 小时 / 前 30 分钟」自然语言，两边没有映射表（N-12）。开发若只读 spec，很可能写成 4 个节点。

### Q3 依赖

- 依赖：**M4**。§2.1 写「范围表依赖 M4；module-06 FR-1 仅录公司名/岗位文本，未关联投递（待 spec 补 FR）」。
- **这个依赖是「范围表口径」，不是「接口调用」**。M6 登记只收公司名与岗位文本，并不真的去查 `application` 表。拆任务时不要把「读 M4 的投递记录」写进 M6 的实现任务——那是过度实现。若真要建立关联，得先让 spec 补一条 FR。
- 被依赖：**M8**（经 `v_dashboard` 聚合）。

## M7 · 面经外链

### Q1 交付物清单

| # | 交付项 | 依据 |
|---|---|---|
| 1 | `InterviewNoteController` —— 3 个端点：`GET /api/v1/interview-notes`、`POST /api/v1/interview-notes`、`GET .../{noteId}/reachability` | 4.7 端点总览 |
| 2 | **SSRF 校验器** —— 协议白名单（仅 http/https）、私网与环回、链路本地含 `169.254.169.254`、保留与多播段、重定向 ≤1 次且每跳重校验、DNS rebinding 防护 | 4.7「SSRF 防护」段 |
| 3 | `interview_note` 表 —— **只存外链与来源，不存正文** | 4.7.1「每条仅含外链与来源，不含正文（FR-2）」 |
| 4 | 24 小时探测任务 —— 失效置 `linkStatus = INVALID`、置灰不可点、带「来源已失效」标记 | NFR-2、4.7.1 |
| 5 | 点击 3 秒判定 —— 超 3 秒判失效，给同关键词重检兜底 | AC-4、NFR-3 |
| 6 | 列表筛选 / 分页 / 分组，首屏 ≤1 秒（API 层保证） | AC-1、AC-3、NFR-1 |
| 7 | 空态与降级 —— 无匹配返回空态、画像方向缺失时 `personalizationApplied = false` 且仍支持手动筛选 | AC-3 |
| 8 | 演示数据标识 —— `isDemo = true`，不与真实数据混用 | AC-5 |
| 9 | 来源字段缺失拒绝入库 + 质量告警 | 边界表「面经记录来源字段缺失」（AC-1） |

### Q2 第一条任务

**做 SSRF 校验器（一个可独立测试的组件），并写死「命中任一规则即返回 400、不发起请求、不写库」。**

- 验收标准：**AC-4**（外链失效或来源不可达时提供重检兜底并标记来源）+ 4.7「SSRF 防护」段最后一句（「命中任一规则即拒绝发起请求，返回 400（无业务码），不写库、不产生探测记录」）。
- 为什么排第一：M7 所有对外请求（收录校验、24 小时探测、点击 reachability）都要过这一层。它先落地，后面三个端点才敢发请求；它做在端点里，就要重复三遍且漏一处就出洞。
- 第二条：`POST /api/v1/interview-notes` 收录（AC-1 + 边界行「来源字段缺失」）。
- 第三条：列表筛选分页（AC-1、AC-3）。
- 第四条：24 小时探测（NFR-2）。
- 第五条：点击 reachability 3 秒判定（AC-4、NFR-3）。
- 第六条：空态 / 降级 / 演示数据标识（AC-3、AC-5）。

### Q3 依赖

- 依赖：**M2**。§2.1 写明理由：`module-07` FR-4 要求「基于 M2 画像的方向标签对相关面经做优先排序」，AC-3 规定画像缺失时不做个性化排序。**这是弱依赖**——没有画像也能跑（降级为默认列表），拆任务时不应把它排成阻塞项。
- 被依赖：**无模块直接依赖 M7**（§2.1 里 M7 只出现在 M8 的聚合列表）。M8 经 `v_dashboard` 只读视图取数，不调 M7 的服务。

## 三模块横向对照

| 维度 | M4 | M6 | M7 |
|---|---|---|---|
| 端点数 | 2 | 4 | 3 |
| 第一张表 | `application` + 唯一约束 `(student_id, job_id)` | `interview` + `reminder` + 唯一约束 `(interview_id, node_type)` | `interview_note`（不存正文） |
| 第一条任务的验收 AC | AC-2（+ 边界表「并发重复提交」） | AC-1 / AC-2 / AC-8 | AC-4（+ SSRF 段落） |
| 依赖 | M3 | M4（范围表口径，非接口调用） | M2（弱依赖，可降级） |
| 被依赖 | M5 / M6 / M8 | M8 | 无 |
| 最容易少做的部分 | AC-4（前端联动，不在 M4 接口里） | AC-3 复盘提醒；重试参数（AC-6 有、契约没有） | SSRF 六类防护漏第一类 |
| 与既有评审意见的对应 | R-08 / R-16（唯一索引未落契约） | R-06（重试参数缺）、N-12（nodeType 无映射）、N-13（409 撤码） | R-12（已闭环）、N-05 无关 |

## 结论

三个模块都能只凭仓库材料拆出可执行任务，**每条任务的验收都能指到具体 AC 编号**，没有「靠感觉判通过」的条目。按此记录，G11 第 4 项的「拆任务演练」一条已具备可核查的问答原文，判定可从「无记录」改为「已记录（单人推演底稿，待现场确认）」。
