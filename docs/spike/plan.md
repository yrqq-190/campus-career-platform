## S1 · 并发重复投递只成功 1 条

### 验证目标

证明 `application` 表的唯一约束 `(student_id, job_id)` 加上服务层事务边界，在**单实例、无分布式锁**的 MVP1 部署下，能保证并发两次提交只产生 1 条记录、另一次拿到 409。同时验证 ADR-001 里「乐观锁 + 唯一约束」相对于「悲观锁」「应用层分布式锁」在本场景是否真的更划算。

### 前置条件

- 一台可用的 MySQL 8.0 实例（本地 Docker 即可，不接 RDS）
- 建表脚本含 `UNIQUE KEY uk_student_job (student_id, job_id)`，引擎 InnoDB，隔离级别默认 REPEATABLE READ
- 服务层用 `@Transactional` 包住「判重 + 插入」，唯一约束冲突异常映射为 409 `DUPLICATE_APPLICATION`

### 步骤

1. 建 `application` 表（含唯一约束），确认 `SHOW CREATE TABLE` 里唯一键真实存在。
2. 写一次性并发脚本：同一 `(student_id, job_id)` 起 N=50 个并发请求，同时打 `POST /api/applications`。
3. 记录三个数：HTTP 2xx 次数、409 次数、其他（500 / 死锁）次数。
4. 直接查库：`SELECT COUNT(*) FROM application WHERE student_id=? AND job_id=?`，期望恒为 1。
5. 抓一次唯一约束冲突的原始异常（`DuplicateKeyException`），确认映射后的响应体里 `code` 是 `DUPLICATE_APPLICATION` 而不是 500。
6. 补测事务回滚：构造「插入成功后立刻做一次非法状态流转」的组合请求，确认失败时状态字段不动、不留下半写记录。

### 成功标准

- 库中同一 `(student_id, job_id)` 记录数恒等于 1；
- N=50 并发中成功恰好 1 次、409 恰好 49 次、500 为 0；
- 409 响应体错误码能对上契约里写的 `DUPLICATE_APPLICATION`；
- 回滚测试后无脏数据、无死锁遗留。

### 结论

**待跑（计划 D2 起执行，D3 收口）**。

跑完要回答三件事：
1. 唯一约束是否足够，需不需要额外的乐观锁版本号；
2. 悲观锁 / 分布式锁在本场景（单实例、低并发、要可演示）代价是否明显更高，ADR-001 的决策依据能否被这次结果支撑；
3. 如果结论是唯一约束足够，ADR-001 的「待验证项」改成「已验证」。

### 产物

`docs/spike/spike-01-concurrency.md`（步骤记录 / 实测数据 / 结论 / 对 ADR-001 的修正建议）

## S2 · 接口契约 Mock

### 验证目标

在不连真后端的前提下，用静态 Mock 把契约里最容易被前端误处理的两个响应跑出来，确认前端拿到 409 和重复触发时**有明确提示、不产生第二次提交、不重复渲染**；顺带把契约里缺的响应字段暴露出来。

### 前置条件

- M4、M6 契约小节已补齐（D2 交付，含成功 / 失败 / 错误码）
- 一份不依赖后端的 Mock：静态 JSON + 一个能起 localhost 的最小服务（`npx serve` / FastAPI / 任意静态方案均可），产物放 `docs/spike/`

### 步骤

1. Mock `POST /api/applications`：正常返回 201 + 记录体；第二次请求返回 `409 {code: "DUPLICATE_APPLICATION", message: "该岗位已登记投递"}`。
2. Mock `POST /api/interviews`：登记成功返回 201 + 5 个节点的 `scheduled_at`；重复触发同节点时返回**幂等结果**（不新增 reminder）。
3. 写一个极简页面（单 html + fetch）调这两个接口，观察：
   - 409 是否有可见提示、按钮是否被禁用、有没有悄悄重发一次；
   - 同一节点重复触发时页面会不会重复弹提醒；
   - 响应体里前端真正需要的字段（记录 id、状态文案、节点列表）是否都在。
4. 把「契约里写了但前端用不上」和「前端需要但契约没写」的字段各列一张清单。

### 成功标准

- 409 触发时页面有明确提示，且不产生第二条记录、不重复提交；
- 重复触发同节点时页面只提醒一次；
- 产出两张字段清单，能直接反馈给 M4 / M6 契约主笔（赵蔚、卢果）；
- Mock 响应结构可直接作为第 10 周前后端联调的样例。

### 契约现状（D1 核对结果，先记在这）

- **M6 契约里不存在 409**。spec/module-06 的幂等是「唯一约束 + 记录已发送状态」，失败重试返回的是 `REMINDER_SEND_FAILED`。所以 S2 对 M6 的部分**不按 409 设计**，改为验证「同一节点重复触发时的幂等返回 + 前端不重复提醒」。这一点与任务卡原描述不同，已在结论段说明。
- **M4 错误码存在两套**：`spec/module-04` 的 AC-2 / 边界表写 `409 ALREADY_APPLIED`、AC-3 写 `409 INVALID_STATUS_TRANSITION`；`docs/architecture.md` 5.4 写 `409 DUPLICATE_APPLICATION` / `409 INVALID_STATE_TRANSITION`。S2 的 Mock 按架构口径（`DUPLICATE_APPLICATION`）做，但这条不一致必须进《契约-Spec 对照表》待修清单，否则第 10 周前后端会各写一个码。

### 结论

**待跑（依赖 D2 契约补齐）**。

### 产物

`docs/spike/spike-02-contract-mock.md` + `docs/spike/mock/`（静态 Mock 与页面，仅存档，不进 src）

## S3 · 提醒基准字段与逾期数据

### 验证目标

确认 M6 五个提醒节点所需的时间基准**真的落在数据实体上**，而不是只写在需求里；确认「已过期节点不触发」有可用的字段支撑；确认 AC-8「未填出发时间」的降级计算能实现。

### 前置条件

- `interview` 表字段清单（至少：start_time、depart_time、status、location、company、position）
- `reminder` 表字段清单（至少：interview_id、node_type、scheduled_at、send_status、sent_at）
- M6 AC-2 / AC-8 / AC-9 与 NFR-1 的基准口径

### 步骤

1. 核对字段：`interview` 是否有独立的 `depart_time`，是否允许为空；`reminder` 是否有能区分「未发送 / 已发送 / 已失效」的状态位。
2. 按 NFR-1 口径算五个节点：前 3 天 / 前 1 天 / 前 30 分钟基于 `start_time`，前 2 小时基于 `depart_time`，复盘在结束时间 + 2 小时。
3. 构造四组数据跑一遍计算：
   - 组 A：完整填写（开始 + 出发都有）；
   - 组 B：未填出发时间（验证 AC-8 退回 `start_time` 并提示）；
   - 组 C：面试时间早于当前（验证「设定的提醒时间已过」的提示）；
   - 组 D：改期（验证 AC-9 旧节点置失效、只重算未来节点、已过期的不补发）。
4. 检查「逾期数据」：库里是否留着已经过了 `scheduled_at` 但 `send_status` 仍未发送的记录——如果有，扫描任务会不会把它们当待发送补发出去。
5. 记录需要补的字段（如果缺）和需要补的状态位。

### 成功标准

- 五个节点都能从现有字段算出触发时间，无一处需要「临时约定」；
- 未填 `depart_time` 时前 2 小时能正确退回 `start_time`，且有用户提示；
- 改期后旧 reminder 全部置失效，不产生重复推送；
- 逾期未发送的 reminder 有明确处理口径（跳过还是补发），并写进结论。

### 结论

**待跑（D2–D3）**。

预估风险点（D1 读过架构第 55 行与 spec AC-8 后记下）：`interview` 实体在 architecture.md 只写了「含开始时间与出发时间」，没写 `depart_time` 是否可空；若不可空，AC-8 的降级路径就没有数据基础。这是本探针最可能翻车的地方。

### 产物

`docs/spike/spike-03-reminder-baseline.md`（字段核对表 / 四组计算结果 / 结论 / 需补字段清单）
