# S1 · M4 投递登记并发幂等

## 1. 验证目标

验证 `ADR-001` 的结论——「乐观锁 + 唯一约束 `(student_id, job_id)`」在高并发重复提交下能否保证**只写入一条记录**，并确认 `DuplicateKeyException` 能被服务层捕获后返回 **409 `ALREADY_APPLIED`** 而非 500。

同时回答一个决策层问题：在单实例、校园规模下，唯一约束是否已经足够，悲观锁（备选 A）与分布式锁（备选 C）的代价是否确实不划算——这决定 ADR-001 的「待验证项」能否标为已验证。

## 2. 假设

- **H1**：数据库唯一约束是硬保证。两个请求同时提交同一 `(student_id, job_id)`，必然只有一个 insert 成功，另一个被约束拒绝——不依赖应用层判重的时序。
- **H2**：`DuplicateKeyException` 能被服务层稳定捕获并映射为 409 `ALREADY_APPLIED`，不泄漏为 500，也不出现「异常吞掉但返回 201」的假成功。
- **H3**：乐观锁版本号冲突时返回 409 `INVALID_STATUS_TRANSITION`，原记录的状态字段与版本号均不变。

三条假设任一不成立，ADR-001 的决策就要重判。

## 3. 方法步骤

1. 建临时表 `application`，加唯一索引 `uk_student_job (student_id, job_id)`，引擎 InnoDB，隔离级别用默认 REPEATABLE READ。用 `SHOW CREATE TABLE` 确认索引真实存在。
2. 用 **10 个线程**同时提交同一 `(student_id, job_id)`，重复 **100 轮**（合计 1000 次提交）。
3. 每轮统计四个数：实际写入行数、2xx 成功响应数、409 响应数、500 响应数。
4. 对已存在的记录并发修改状态（多个线程同时把「已投递」往不同目标状态改），验证版本号冲突路径。
5. 抓一次 `DuplicateKeyException` 的原始堆栈，确认映射后的响应体 `code` 为 `ALREADY_APPLIED`。
6. 补一组回滚测试：构造「插入成功后立刻做非法状态流转」的组合请求，确认失败时状态与版本号都不动、不留半写记录。

## 4. 成功判据与产出

**成功判据**

- 每轮实际写入行数**恒为 1**；
- **500 响应数为 0**；
- 409 `ALREADY_APPLIED` 响应数 = 提交数 − 1（即 9/轮，900/总）；
- 状态冲突场景返回 409 `INVALID_STATUS_TRANSITION`，且状态字段与版本号均未变更；
- 回滚测试后无脏数据、无死锁遗留。

**产出**

`docs/spike/results.md` 的 §S1，含：
1. 实测数据表（每轮写入行数 / 成功数 / 409 数 / 500 数）；
2. 环境说明（MySQL 版本、隔离级别、线程与轮次）；
3. **结论三选一**：支持 / 不支持需换方案 / 部分支持需补条件；
4. 对 ADR-001「待验证项」的处置建议：转「已验证」还是改写决策。

**时间盒**：D3 内完成。超出时间盒则**缩小并发规模**（如降到 5 线程 × 50 轮），**不延期**。

**约束**：全程不碰 `src/`，不新增业务生产代码；建表与压测脚本为一次性脚本，跑完只保留数据与结论。

# S2 · 接口契约 Mock

## 1. 验证目标

在不连真后端的前提下，用静态 Mock 把契约里最容易被前端误处理的两个响应跑出来，确认前端拿到 409 和重复触发时**有明确提示、不产生第二次提交、不重复渲染**；顺带把契约里写多了和写漏了的字段暴露出来。

## 2. 假设

- **H1**：契约给出的 409 响应体（`code` + `message`）足够前端渲染出一句用户能看懂的提示，不需要前端自己拼文案。
- **H2**：M6 同一节点重复触发时，接口按幂等返回（不新增 reminder），前端不会因此重复弹提醒。
- **H3**：契约里的成功响应字段能覆盖前端展示所需，不需要前端再额外请求一次。

## 3. 方法步骤

1. 起一个最小静态 Mock（`npx serve` 或任意本地静态服务），产物放 `docs/spike/`。
2. Mock `POST /api/v1/applications`：正常返回 201 + 记录体；第二次返回 `409 {code:"ALREADY_APPLIED", message:"该岗位已登记投递"}`。
3. Mock `POST /api/v1/interviews`：登记成功返回 201 + 5 个节点 `triggerAt`；同节点重复触发返回幂等结果（不新增 reminder）。
4. 写一个极简页面（单 html + fetch）调这两个接口，观察：409 是否有可见提示、按钮是否被禁用、有没有悄悄重发；重复触发时页面是否重复弹提醒；响应体字段是否够用。
5. 列两张清单：契约写了但前端用不上的字段 / 前端需要但契约没写的字段。

## 4. 成功判据与产出

**成功判据**

- 409 触发时页面有明确提示，且不产生第二条记录、不重复提交；
- 重复触发同节点时页面只提醒一次；
- 两张字段清单能直接反馈给 M4 / M6 契约主笔。

**产出**

`docs/spike/results.md` 的 §S2：Mock 截图或响应样例 + 两张字段清单 + 结论。

**时间盒**：D3 内。**约束**：Mock 与页面只在 `docs/spike/` 存档，不进 `src/`。

# S3 · 提醒基准字段与逾期数据

## 1. 验证目标

确认 M6 五个提醒节点所需的时间基准**真的落在数据实体上**，而不是只写在需求里；确认「已过期节点不触发」有可用的字段支撑；确认 AC-8「未填出发时间」的降级计算可实现。

## 2. 假设

- **H1**：`interview` 有独立的 `depart_time` 且允许为空，否则 AC-8 的降级路径没有数据基础。
- **H2**：`reminder` 有能区分「未发送 / 已发送 / 已失效」的状态位，可与 `scheduled_at` 一起判定过期。
- **H3**：按 NFR-1 口径（前 3 天 / 前 1 天 / 前 30 分钟按开始时间，前 2 小时按出发时间）能从现有字段算出全部五个节点。

## 3. 方法步骤

1. 核对 `interview` 与 `reminder` 的字段清单，逐项确认是否存在、是否可空。
2. 按 NFR-1 口径算五个节点。
3. 构造四组数据：A 完整填写、B 未填出发时间、C 面试时间早于当前、D 改期。
4. 检查逾期数据：库里是否留着已过 `scheduled_at` 但 `send_status` 仍未发送的记录，扫描任务会不会补发。
5. 记录需要补的字段与状态位。

## 4. 成功判据与产出

**成功判据**

- 五个节点都能从现有字段算出，无一处需要「临时约定」；
- 未填 `depart_time` 时前 2 小时正确退回 `start_time` 且有提示；
- 改期后旧 reminder 全部置失效，不产生重复推送；
- 逾期未发送的 reminder 有明确处理口径（跳过还是补发）。

**产出**

`docs/spike/results.md` 的 §S3：字段核对表 + 四组计算结果 + 需补字段清单 + 结论。

**时间盒**：D3 内。**约束**：只做字段与计算核对，不写实现。

# S4 · 大模型超时与乱码降级

## 1. 验证目标

验证 `adr/ADR-002` 的三条约束在真实时序下是否站得住：30 秒超时 + 重试 2 次 + JSON Schema 校验。要回答的不是「码对不对」（契约 4.1 与 ADR-002 已一致，都是 `504 PARSE_TIMEOUT` / `502 MODEL_OUTPUT_INVALID`），而是**最坏要等约 92 秒时，用户看到的界面是否还可用**——这决定 ADR-002 「同步请求」这条决策是否真的能落到演示上。

## 2. 假设

- **H1**：最坏 92 秒（30×3 + 1×2 间隔）等待期间，前端有持续 loading 与阶段提示，用户不会误判为卡死而重复提交。
- **H2**：504 与 502 两个响应都带「可重试」语义，前端能给出重试入口，且重试不会产生第二条暂存记录。
- **H3**：无论 504 还是 502，正式档案与暂存区都保持上传前状态，不出现半成品被写入。

## 3. 方法步骤

1. Mock 三个响应：① 延迟 31 秒后超时（模拟第一次超时）；② 连续三次超时后返回 `504 PARSE_TIMEOUT`；③ 返回非法 JSON（如 `"这是一份简历"`）触发 `502 MODEL_OUTPUT_INVALID`。
2. 用极简页面调 `POST /api/v1/resumes`，记录从点击到出提示的实际秒数。
3. 观察加载期间的界面状态：有无 loading、有无阶段文案、按钮是否置灰。
4. 拿到 504 / 502 后点重试两次，检查是否出现重复的暂存记录。
5. 检查响应体是否含 `requestId`、`retryable` 等前端可用字段。

## 4. 成功判据与产出

**成功判据**

- 92 秒内界面持续有反馈，不出现无提示白屏；
- 提交按钮在请求期间置灰，不会因用户连点产生重复请求；
- 504 / 502 都能显示可读文案 + 重试入口；
- 重试后暂存记录仍只有一条；
- 失败时正式档案与暂存区状态不变。

**产出**

`docs/spike/results.md` 的 §S4：三组实测秒数 + 界面状态记录 + 结论。若 H1 不成立（92 秒体验不可接受），结论要直接写成「ADR-002 需补前端约束或改异步」，不改结论去迁就决策。

**时间盒**：D3 内，可缩到只测第 ③ 组（乱码降级），超时组用 Mock 延迟压缩到 5 秒等比验证。**约束**：Mock 与页面只在 `docs/spike/` 存档。
