# PR 准入条件清单（8 条）

> 归属：颜睿卿（第 9 周）
> 依据：课件 P5「PR 准入」要求 + 四天分工表第五节
> 版本：v1.0（2026-11-19）
> 用法：**第 10 周评审演练直接照此执行**；第 9 周首条 PR（T2）即按此演练。
> 配套：`.github/PULL_REQUEST_TEMPLATE.md`（模板已预置四栏，对应第 1、2、3、4 条）

## 一、8 条准入

| # | 准入条件 | 谁来保证 | 怎么判（可执行） |
|---|---|---|---|
| 1 | **关联 Issue 和对应 spec/AC** | 提交人 | PR 描述**首行**有 `Issue: #<编号>`，且有 `AC: <编号列表>`（如 AC-1、AC-3）。空 Issue 号、只写「相关」、写不出 AC 编号 → 不通过 |
| 2 | **变更摘要：改了什么、为什么改** | 提交人 | 描述里有「改了什么」与「为什么改」两段，能对上 Issue 里写的问题；只贴文件清单不算 |
| 3 | **AI 使用说明：工具、提示词、人工修改处** | 提交人 | 三要素齐全：用了什么工具、提示词要点、**人工改了什么**。写「未使用 AI」也算合规答卷，但不能留空 |
| 4 | **测试证据：命令、输出、截图** | 提交人 | 有可复现命令 + 实际输出（或截图）。只写「已测试」「本地跑通」不算证据 |
| 5 | **至少 1 人人工评审** | 交叉评审人 | PR 上有 `Approved` 记录，且评审人 ≠ 提交人、≠ 本模块主笔（模块作者不自评） |
| 6 | **Agent 评审对照 spec/AC 逐条核** | 评审人 | 评审评论里逐条列 AC 与结论（对上 / 对不上 / 缺证据）。整条「看着没问题」不算 |
| 7 | **无越界修改** | 评审人 | diff 里不得出现：`architecture.md` 第 4 章契约、第 3 章数据实体、`spec/` 目录、他人模块目录。出现即不通过 |
| 8 | **评审不通过优先改 spec，不硬改代码** | Spec Owner | 若结论是「代码对、spec 没写清」，先提 spec 修订 PR；直接改代码去迁就实现即不通过 |

## 二、执行顺序

**提交人自查（1–4）→ 评审人复核（5–8）**，顺序不可跳。

- 1–4 任一条缺失：评审人可直接退回，不必逐条核 AC（省评审时间）；
- 5–8 任一条不通过：在 PR 评论里写明「不通过的是第几条 + 具体位置」，提交人改后在原 PR 继续，不重开；
- 第 7 条若确需动契约：先按第 8 条走 spec 修订，再回来改代码，PR 描述里附 spec PR 号。

## 三、各角色的动作

| 角色 | 在 PR 里的动作 |
|---|---|
| 提交人 | 按模板填 4 栏；自查 8 条并勾选；把 Issue 拖进 In Progress，开 PR 后立即拖进 Review |
| 交叉评审人 | 只核 5–8；第 6 条必须逐条列 AC 结论；给出 `Approve` 或 `Request changes` |
| Spec Owner | 判第 8 条：结论是否该改 spec；改 spec 后回填 AC 编号 |
| 记录人（颜睿卿） | 把评审意见记到 `docs/review/pr-<编号>.md`，进 Done 时核对验收证据 |

## 四、高频打回原因（自查时先自己排掉）

1. **Issue 号写了但 AC 编号没写** → 第 1 条不通过；
2. **AI 使用说明只写「用了 AI」** → 第 3 条不通过，缺「人工修改处」；
3. **测试证据是截图但没有命令** → 第 4 条只算半条，评审人可要求补命令；
4. **PR 里顺手改了 `architecture.md` 的契约** → 第 7 条不通过，且触发冻结范围红线；
5. **作者自评自签**（M1/M2 的 PR 由贾小舒自己 Approve） → 第 5 条不通过；
6. **AC 对不上时直接改代码迁就** → 第 8 条不通过，应回头改 spec。

## 五、与冻结范围的关系

`architecture.md` §8 冻结范围内的事项（模块边界、接口契约、依赖方向、关键 ADR、核心数据实体与唯一约束）本周**不得擅自改**。PR 需要动这些内容时，第 7 条判不通过，按「新增 ADR 留痕」或「spec 先改」处理，不豁免准入。
