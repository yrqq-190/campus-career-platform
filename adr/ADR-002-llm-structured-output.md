# ADR-002 大模型结构化输出：超时、重试与降级

## 状态
已接受 (Accepted)

## 背景
本系统在 M1 简历解析等模块需调用大模型（LLM）抽取结构化数据。大模型 API 存在极大的不确定性，具体表现为：**1. 网络超时**（响应慢导致系统卡死）；**2. 格式漂移**（未按要求返回 JSON，而是返回自然语言或多出多余解释）；**3. 输出截断**（因 Token 长度限制，返回的 JSON 不完整导致解析报 500 错误）。如果不加约束，会导致脏数据入库或系统崩溃。需要决定系统与大模型交互时的超时、重试与降级策略。

## 备选方案

### 备选 A：同步请求 + 无重试 + 无校验
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 直接请求大模型，拿到什么返回什么 | 实现极简，响应最快 | 网络一抖动直接报错；模型返回乱码或截断直接导致系统崩溃或脏数据 | 仅供本地测试，不可用于生产 |

### 备选 B：同步请求 + 超时重试 + JSON Schema 校验（推荐）
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 设定 30 秒超时、最多重试 2 次、返回后强制过 JSON Schema 校验 | 容错率高，能拦截绝大多数幻觉和格式错误；架构简单，符合 MVP1 单实例要求 | 用户在最坏情况下需等待约 92 秒；占用服务器线程 | MVP1 演示、小规模并发业务 |

### 备选 C：异步队列 + 回调通知
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 提交任务进队列，后台慢慢请求大模型，完成后回调前端 | 不阻塞用户，后端压力极小 | 架构复杂度极高（需引入 MQ），前端需做轮询或 WebSocket，开发和演示成本过大 | 高并发、大文件批处理场景 |

## 决策
采用**备选 B：同步请求 + 超时重试 + JSON Schema 校验**。
1. **决策参数**：大模型调用超时固定为 **30 秒**，失败最多重试 **2 次**，重试间隔 **1 秒**。大模型必须返回结构化 JSON，服务层必须通过 **JSON Schema 校验**才可返回前端或入库。
2. **降级处理**：超时重试耗尽返回 `504 PARSE_TIMEOUT`；格式校验失败返回 `502 MODEL_OUTPUT_INVALID`。降级时原数据状态不变，不产生半成品。（注：与 M1 契约完全一致）
3. **成本与幂等边界（N-06）**：同一份简历最多触发 3 次大模型调用。**重试期间复用同一次请求的暂存上下文，绝不重复解析入库，成本上限锁定为 3 次调用/请求。**

## 决策依据 (Trade-off)
**正面**：通过服务层强校验，彻底杜绝了前端展示半成品或脏数据，提升了系统稳定性。
**负面**：在极端网络情况下（重试 2 次均超时），用户最坏需等待 **92 秒（30×3+1×2 = 92 秒）**。此等待时长已评估可接受，但强制要求 `architecture.md` 的 4.1 契约中，前端必须实现：请求期间显示 Loading、提交按钮置灰防连点、超时后明确给出错误提示，杜绝白屏等待**（N-05）**。
**为什么否掉 A 和 C**：A 完全不可用；C 对于 MVP1 架构来说属于过度设计。MVP1 阶段业务量小，选 B 是稳定性与开发成本的最优解。
