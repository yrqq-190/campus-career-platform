# 仓库目录约定

## 背景

产品边界、功能规格、技术决策与实现代码承担不同用途。明确目录职责有助于查找依据、评审变更并避免实验代码与应用代码混杂。

## 决策

| 路径 | 内容 |
| --- | --- |
| `README.md` | 项目入口、内容说明与文档导航 |
| `context.md` | 用户场景、产品范围与业务约束 |
| `agent-rules.md` | AI 辅助开发规则 |
| `spec/` | 功能输入、输出、异常行为与验收条件 |
| `adr/` | 对架构产生持续影响的决策 |
| `plans/` | 与具体目标关联的实施方案与依赖分析 |
| `src/` | 可维护的业务实现 |
| `tests/` | 与业务行为相关的测试和验证 |
| `docs/` | 开发、使用及技术文档 |
| `docs/spike/` | 技术探针、实验结论与复现方式 |
| `.github/` | GitHub Issue 与 Pull Request 等协作配置 |
| `CONTRIBUTING.md` | 面向贡献者的参与与验证要求 |

目录按产品资料、工程实现与平台配置的用途组织。具体前后端子目录应与可运行工程配置一并确定，不仅为占位而创建多个空工程。

## 理由与影响

规格和决策可独立于实现被评审；技术探针保留假设与限制，不直接作为业务实现完成的依据。GitHub 配置集中在约定路径，避免把平台模板混入业务规格。

新增目录应有明确用途并更新文档导航。涉及架构职责变化时补充决策说明；普通内容调整无需为每个文件创建一条决策记录。
